### 第二轮:实测仍是"老样子",根因在 Reload(同日)

P15-1..6 落地后用户实测**仍与旧方案完全一样**。查真实数据目录:`Profiles/1`、`Profiles/2`
确实只有 `appSettings.json` + `layout.json`(播种正确,组件数据没被复制),但两份 `layout.json`
与 `Profiles/Default/layout.json` **字节级完全相同**,含同样 5 个组件同 `InstanceId`。

用真实 `WidgetFactory` + 真实组件窗口写了临时复现程序(`tests/_profilerepro`,排查后已删除),
把每次 `layoutProvider.Save` 的调用栈、当前方案、组件数打出来,得到决定性证据:切方案后
`Const.LayoutFile` 已指向新方案、磁盘文件是 0 个组件,但 `layoutProvider.Get()` 仍返回 2 个,
`RELOAD` 一次都没触发 —— **`SwitchProfile` 里的"重新读取"是空转**。

根因:`IDataProvider<T>.Reload()` 是 `void` 的默认接口实现(`public void Reload() { }`),
而 `JsonParser<T>.Reload()` 的签名是 `public virtual T Reload()` —— 返回 `T` **不能**隐式实现
`void`,于是接口映射落到默认空实现上。凡是拿着 `IAppSettingsProvider`/`ILayoutProvider` 调
`Reload()` 的地方(只有 `ProfileService.SwitchProfile` 与 `RenameProfile`)全部静默 no-op。
后果链:内存里始终是旧方案的设置与布局 → 第 6 步 `displayMonitor.Refresh()` 把旧布局当作当前
布局回写(`RefreshCore` 的"回填即保存") → **旧桌面被写进新方案目录**;第 8 步
`CreateFromLayout()` 再从旧布局重建窗口 → 用户看到"新建的方案和刚才一模一样"。

| # | 改动 | 文件 | 说明 |
|---|---|---|---|
| P15-7 | 让 `Reload` 真正实现接口 | `DeskCanvas.Core/Services/JsonParser.cs` | 增加显式接口实现 `void IDataProvider<T>.Reload() => Reload();`,接口调用走真实重载(保留 `T Reload()` 供具体类型使用);不改公共 API 面(基线仍 1440 行) |
| P15-8 | 切换前补齐方案文件 | `Services/ProfileService.cs` | 抽出 `SeedMissingProfileFiles()`,`CreateProfile` 与 `SwitchProfile` 共用:目录存在但缺 `appSettings.json`/`layout.json`(手工建的、残缺导入)时先播种,避免 Reload 抛异常后留下"指针已切、组件已关"的半切换状态 |
| P15-9 | 断言补强到能抓住这个 bug | `tests/ProfileStorageChecks/Program.cs` | 旧断言在"切回默认值恰好等于旧缓存"时恒真。改为:当前方案置 0.93 + `#123456` 且**确实带 1 个组件**,切到新方案后断言内存设置回到 0.4、强调色清空、内存布局 0 组件、旧方案文件仍保留其组件;再切回断言 0.93 与组件恢复。另加残缺目录用例 5 项 |
